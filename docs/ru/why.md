# Почему именно он?

[← К документации](README.md)

**Один прогон вместо трёх.** Разный RPS на разные методы одновременно. В `ghz` — один метод на
запуск, и смесь нагрузки просто не выражается. В `k6` выражается, но скриптом на JavaScript,
который придётся написать и поддерживать.

**Цифры, которым можно верить.** Латенси считается от момента, на который запрос был
*запланирован*, а не от момента, когда его удалось отправить. Разница не косметическая: при
зависании сервиса на секунду наивный замер показывает `p99 = 5ms` вместо честных `1005ms`.
Подробности — в [списке проблем](pitfalls.md).

**Ноль подготовки.** Ни `.proto`, ни кодогенерации, ни скриптов. Адрес сервиса, имя метода — и
всё: описание метода инструмент спрашивает у самого сервиса через gRPC server reflection. Язык,
на котором написан сервис, роли не играет.

**Конфиг, а не программа.** Нагрузка описывается декларативно, в одном файле, который лежит
рядом с кодом и читается через полгода. В `k6` это скрипт; скрипт — это код, который надо
дебажить, ревьюить и чинить, когда он сам станет узким местом.

**Годится для CI из коробки.** Задал `p99 < 200ms` — превышение роняет пайплайн кодом возврата.
Не надо парсить вывод регулярками и писать обвязку на bash.

**Сделано для людей.** Ошибка конфига называет файл, строку и то, что именно не так. Опечатка в
имени поля — это ошибка, а не молчаливый пустой прогон с зелёным отчётом. Во время прогона видно,
что происходит, а не «тишина, потом стена цифр». Мы считаем плохое сообщение об ошибке дефектом,
а не мелочью.

| | ghz | k6 | JMeter | grpc-loadgen |
|---|---|---|---|---|
| Разный RPS на разные методы в одном прогоне | нет | скриптом | неудобно | **да** |
| Латенси без coordinated omission | частично | closed model по умолчанию | нет | **да** |
| Без `.proto` и кодогенерации | да | нет | нет | **да** |
| Связывание вызовов по данным | нет | вручную в скрипте | вручную | **этап 1** |
| Пороги для CI | частично | да | плагинами | **да** |
| Конфиг вместо кода | да | нет | XML в GUI | **да** |
