# Какую проблему решает LeetTest?

[← К документации](README.md)

Нагрузочный тест нужен, чтобы ответить на один вопрос: **при какой нагрузке сервис перестаёт
справляться и где узкое место.** С этим ответом идут к разработчикам — чинить, оптимизировать,
решать, выпускать ли релиз.

Чтобы ответ был правдой, нужны две вещи.

**Нагрузка, похожая на настоящую.** Реальный сервис никогда не нагружают одной ручкой. В
платёжном сервисе в любой момент идут сотни запросов баланса, десятки переводов и единицы
регистраций — и ломается он на этой смеси, а не на каждом методе по отдельности. Сервис, который
держит 800 RPS на чтении и 50 RPS на записи по отдельности, может лечь на их сумме — из-за общего
пула соединений, блокировок в базе, конкуренции за один кеш. `ghz` берёт один метод на запуск:
три метода — три прогона и ни одного ответа на вопрос, что происходит, когда они идут вместе.
LeetTest описывает нагрузку целиком: список методов, у каждого свой RPS, один прогон, один
отчёт.

**Числа, которым можно верить.** Нагрузочный инструмент выдаёт число, на основании которого
принимают решение. Если оно получено неправильно, оно опаснее отсутствия числа: отсутствие
видно, а неправильное выглядит как знание. Самые дорогие ошибки случаются ровно в момент
деградации — когда сервис начинает тормозить, а инструмент продолжает показывать красивые цифры.
Про конкретные способы соврать — [отдельная страница](pitfalls.md).

Чего инструмент не делает: он видит сервис только снаружи — задержки, пропускную способность,
ошибки. Загрузку CPU и памяти сервиса он не видит и не угадывает по своим данным. Её берут из
мониторинга сервиса и сопоставляют с нагрузкой по времени.
