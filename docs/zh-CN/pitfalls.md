# 它修正了压测中的哪些问题？

[← 返回文档](README.md)

下面列出压测工具在哪些地方会撒谎或碍事，以及我们各自处于什么状态。

状态如实标注：`已完成` 表示现在就能用；`进行中` 表示正在编写；`已规划` 表示方案已定、代码尚未落地。

| 问题 | 状态 |
|---|---|
| Coordinated omission：故障时段从报告中消失 | 进行中 |
| 每次运行只能一个方法：无法表达混合负载 | 进行中 |
| closed model 恰好在服务劣化时自行减压 | 进行中 |
| 压测机被挂起请求拖垮，先于被测服务倒下 | 已规划 |
| 分位数被平均，失去意义 | 已规划 |
| 指标采集拖慢压测机本身 | 已规划 |
| 必须准备 `.proto` 与代码生成 | 已规划 |
| 配置里的一个拼写错误导致空跑却显示通过 | 已完成 |
| 目标服务的限流被算作服务端错误 | 已规划 |
| 冷启动扭曲分位数 | 进行中 |
| 无法基于数据串联调用 | 阶段 1 |
| 运行过程中不知道发生了什么 | 已规划 |

## Coordinated omission

压测中代价最高的错误。目标 1000 RPS，即每毫秒一个请求。服务卡死一秒，
这一秒内本应发出 1000 个请求。

若从请求实际发出的时刻开始计时，它们都在服务恢复后才发出，各耗时 5 毫秒，报告给出 `p99 = 5ms`。
整段故障消失了：工具恰恰在一切都不正常的时候报告一切正常。

我们在计划阶段就为每个请求打上应发时间，并从该时刻开始计时。计划在 `t=0`、实际 `t=1000ms` 发出、
`t=1005ms` 收到响应的请求，其延迟就是 `1005ms`。这一点从第一行代码起就在内核之中——
在做好的引擎上是补不出来的。

## 每次运行只能一个方法

生产环境不是单一接口。单独测试时能扛住 800 RPS 读取与 50 RPS 写入的服务，
可能倒在两者之和上：共享连接池、锁、缓存争用。分开运行无法体现这一点。
我们接受一份方法清单，各自设定 RPS——一次运行，一份报告。

## closed model

"N 个虚拟用户，各自等到响应再发下一个"看起来很自然，却有先天缺陷：服务变慢时，
用户等待更久，实际施加的负载自行下降。工具恰好在最该施压的时候停止了施压。

我们采用 open model：目标速率是一张时刻表，请求按时钟发出，不管先前的是否已返回。

## 压垮压测机自身

open model 的另一面：目标一旦卡住，挂起的请求不断堆积，压测机会先于被测服务倒下。
对策是显式限制并发请求数。关键在于，触及上限属于运行错误，而非悄悄降低负载——
一次"1000 RPS"的运行悄然变成"能跑多少算多少"，比直接失败更糟。

## 分位数与指标

两个 p99 的平均值并不是 p99——它们不能被平均。可以合并的只有分布，
因此跨边界传递的是直方图，分位数由它计算得出。正是这一性质让日后的多机运行成为可能。

此外还有采集的代价。在高速率下，用互斥锁保护一个共享的延迟切片会让压测机成为自己的瓶颈：
它测到的是锁争用，而不是服务。因此我们使用 HDR 直方图与分片计数器。

## 准备工作与拼写错误

无需 `.proto`，无需代码生成：方法定义通过 reflection 从服务获取。

配置以严格模式读取。把 `rps: 800` 写成 `rsp: 800` 会报错并指出位置，
而不是零负载空跑再给一份绿色报告。`rps: 0` 同样是错误：空的成功运行是最糟糕的谎言，
因为它看起来就像成功。

## 错误与预热

目标限流器返回的 `RESOURCE_EXHAUSTED` 与超时或服务崩溃并不是一回事。
把它们统统算作"错误率 12%"就丢掉了含义。报告中这些类别是分开的。

运行的最初几秒总是偏慢：缓存为空、连接正在建立、JIT 尚未预热。
它们会扭曲整次运行的分位数，因此 `warmup` 会把它们排除在报告之外。

## 可见性

一次运行不该是长达十分钟的黑箱。运行期间可以看到当前速率、在途请求数、错误占比和当前 p99——
足以让你在第二分钟就中止一次注定无意义的运行，而不是等到第十分钟。
