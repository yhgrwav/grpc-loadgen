# 什么是调用串联，为什么重要？

[← 返回文档](README.md)

真实服务中有一半的方法无法用静态数据调用。要给转账施加负载，就需要已经存在的钱包：
`Transfer` 需要 `from` 和 `to`，而它们只能来自 `CreateWallet` 的响应。

常见的变通做法是提前准备测试数据并写死在配置里。这能撑到第一个尖锐问题出现为止：
在同样两个钱包之间转账一千次，压的不是转账，而是数据库里的一行及其锁。
只有让不同实体持续流动，才能得到接近真实的结果。

另一种变通是写个脚本，创建钱包后立刻发起转账。那样你测量的是"创建加转账"这一串行过程，
两者对延迟的贡献再也分不开。

我们用池来解决。把某个调用声明为生产者：从它的响应中取出某个字段，累积到一个具名池中。
另一个调用是消费者：它从池中取值填充自己的请求。两者各自保持自己的 RPS，
在报告中也各占一行。

```yaml
calls:
  - method: wallet.v1.WalletService/CreateWallet
    rps: 5
    extract:
      wallets: wallet_id

  - method: wallet.v1.WalletService/Transfer
    rps: 50
    payload:
      from: ${pool.wallets}
      to: ${pool.wallets}
      amount: 100
```

这不需要改动任何人的 `.proto`：关联关系写在我们这边，而方法与字段是否存在会在启动时
依据 reflection 数据校验——缺少字段会在运行开始前给出明确报错，
而不是在压测中途返回一堆垃圾响应。

有一个问题要等实现时才能定下：当消费者快过生产者、池被耗尽时该怎么办——等待、降低负载，
还是直接失败。悄悄复用最后一个值是唯一可以确定错误的答案。
