# 什么是调用串联，为什么重要？

[← 返回文档](README.md)

> 本译文可能落后于[俄文原文](../ru/chaining.md)。

> **状态：已规划，尚不可用。** 下面的示例是格式草案，不是可运行的配置。

真实服务中有一半的方法无法用静态数据调用。要压测转账，需要已存在的钱包：`Transfer`
需要 `from` 和 `to`，而它们只能从 `CreateWallet` 的响应中获得。

常见的办法是提前准备测试数据。在数据可以预先准备的地方，这是正确的路径，为此在串联之前
会先提供从文件注入数据：CSV 或 JSON 数据集，每个请求一行。但并非一切都能预先准备：
一次性令牌、会话、针对创建过程本身的负载。而在同样两个钱包之间转账一千次，压的不是转账，
而是数据库中的一行及其锁。

第二个办法是写脚本，先创建钱包再立刻从它转账。这样你测到的不是转账，而是
"创建加转账"这一序列，两者在延迟中已经无法区分。

我们用池来解决。一个调用被声明为生产者：从它的响应中取出某个字段，收集到命名的池中。
另一个调用是消费者：它把池中的值填入自己的请求。每个调用以自己的 RPS 运行，
在报告中各占一行。

```yaml
calls:
  - method: wallet.v1.WalletService/CreateWallet
    rps: 5
    extract:
      wallets: wallet_id

  - method: wallet.v1.WalletService/Transfer
    rps: 50
    data:
      from: ${pool.wallets}
      to: ${pool.wallets}
      amount: 100
```

这不需要改动别人的 `.proto`：关联关系在我们这边描述，方法和字段是否存在会在启动时
依据 reflection 数据检查——缺少字段就是运行前的明确错误，而不是压测中途的垃圾响应。

一个将随实现一起解决的开放问题：当消费者快于生产者、池被耗尽时怎么办——等待、降低负载
还是失败。悄悄复用最后一个值，是唯一确定错误的答案。
