# grpc-loadgen 解决什么问题？

[← 返回文档](README.md)

没有人会只通过一个接口去压测真实服务。在一个支付服务里，任意时刻都同时存在数百次余额查询、
数十次转账和少量注册——它崩溃的原因正是这种混合流量，而不是某个方法单独承压。

通常使用的工具并非这样工作。`ghz` 每次运行只针对一个方法：三个方法就是三次运行、三份报告，
而对"它们同时发生时会怎样"完全没有答案。一个单独测试时能扛住 800 RPS 读取和 50 RPS 写入的服务，
很可能倒在两者之和上——共享连接池、数据库锁、对同一份缓存的争用。分开运行永远看不到这一点。

grpc-loadgen 把负载作为一个整体来描述：一份方法清单，每个方法有各自的 RPS 和持续时间，
在一次运行、一份报告中完成。这才是真正的差别——不是"更快"或"更方便"，
而是能提出其他工具无法表达的问题。

问题的另一半是能否相信这些数字。压测工具给出的数值往往决定某个版本是否发布。
用错误方式得到的数值比没有数值更危险：缺失是看得见的，而错误的数值看起来像知识。
这些工具具体如何撒谎，[另有一页说明](pitfalls.md)。
