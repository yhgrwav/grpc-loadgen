# LeetTest 解决什么问题？

[← 返回文档](README.md)

> 本译文可能落后于[俄文原文](../ru/problem.md)。

压测是为了回答一个问题：**服务在多大负载下开始扛不住，瓶颈在哪里。**
拿着这个答案去找开发者——修复、优化、决定是否发布。

要让答案真实，需要两样东西。

**接近生产的负载。** 没有人只用一个接口去压一个真实服务。支付服务在任意时刻都有数百个
余额查询、数十笔转账和寥寥几次注册——它是在这种混合负载下崩溃的，而不是在单个方法上。
一个分别能扛住 800 RPS 读和 50 RPS 写的服务，可能在两者叠加时倒下——因为共享的连接池、
数据库锁、对同一缓存的争用。`ghz` 每次运行只测一个方法：三个方法就是三次运行，
却没有回答它们同时运行时会发生什么。LeetTest 描述完整的负载：一个方法列表，
每个方法各自的 RPS，一次运行，一份报告。

**可以信任的数字。** 压测工具给出的数字是决策的依据。以错误方式得到的数字比没有数字更危险：
没有数字一眼可见，错误的数字却看起来像知识。代价最高的错误恰恰发生在劣化时——服务变慢，
工具却继续显示漂亮的数字。具体的撒谎方式见[单独一页](pitfalls.md)。

工具不做的事：它只从外部观察服务——延迟、吞吐、错误。它看不到服务的 CPU 和内存，
也不会从自身数据中猜测它们。这些数据来自服务的监控，按时间与负载对齐。
