# 为什么选择它？

[← 返回文档](README.md)

**一次运行顶三次。** 多个方法各自不同的 RPS，同时进行。`ghz` 每次只能跑一个方法，
根本无法表达混合负载；`k6` 可以，但要靠一段需要你编写和维护的 JavaScript 程序。

**可信的数字。** 延迟从请求被*计划*的时刻开始计算，而不是从它实际发出的时刻。
这个差别绝非细节：服务卡死一秒时，朴素的测量方式会给出 `p99 = 5ms`，而诚实的答案是 `1005ms`。
详见[问题清单](pitfalls.md)。

**零准备。** 不需要 `.proto`，不需要代码生成，不需要写脚本。只要地址和方法名——
工具会通过 server reflection 直接向服务获取方法定义。被测服务用什么语言实现并不重要。

**是配置，不是程序。** 负载以声明式方式写在一个文件里，它和代码放在一起，半年后依然读得懂。
在 `k6` 里那是一段脚本，而脚本就是代码：需要调试、需要评审，等它自己成为瓶颈时还得修。

**天生适配 CI。** 设定 `p99 < 200ms`，一旦突破就通过退出码让流水线失败。
不必用正则解析输出，也不必写 bash 胶水代码。

**为人而造。** 配置出错时会指出文件、行号以及具体哪里不对。字段名写错是错误，
而不是一次悄无声息的空跑加一份绿色报告。运行过程中你能看到正在发生什么，
而不是先一片沉寂、最后甩出一堵数字墙。我们把糟糕的错误提示视为缺陷，而不是小事。

| | ghz | k6 | JMeter | grpc-loadgen |
|---|---|---|---|---|
| 一次运行中各方法不同 RPS | 不支持 | 靠脚本 | 笨重 | **支持** |
| 不受 coordinated omission 影响的延迟 | 部分 | 默认 closed model | 不支持 | **支持** |
| 无需 `.proto` 与代码生成 | 支持 | 不支持 | 不支持 | **支持** |
| 基于数据的调用串联 | 不支持 | 脚本里手工实现 | 手工 | **阶段 1** |
| CI 阈值 | 部分 | 支持 | 靠插件 | **支持** |
| 用配置而非代码 | 支持 | 不支持 | GUI 里的 XML | **支持** |
