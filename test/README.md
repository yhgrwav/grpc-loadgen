# <img src="../assets/icon.png" width="24" alt="" align="top"> Эталонный стенд и тесты корректности измерений

Здесь живёт не проверка функциональности, а проверка того, что инструмент не врёт. Продукт —
измерительный прибор, и главный вопрос к нему один: совпадают ли числа в отчёте с тем, что
происходило в действительности.

## Что здесь есть

**`stand/`** — эталонный gRPC-сервис с управляемым поведением: постоянная задержка, зависание,
отказ заданным кодом по расписанию, смена задержки в середине прогона. Поведение задаётся
построением, а не утверждается, поэтому правильный ответ известен заранее: стенд, которому велено
держать ответ 200 мс, не высказывает мнение о правильном числе, а создаёт его.

Стенд не зависит от кода движка — только от контракта `grpc.health.v1.Health/Check` и server
reflection, — поэтому на него можно натравить и другой инструмент.

**`measure/`** — тесты-подстановки: полный путь (планировщик → пул воркеров → gRPC-отправитель →
метрики) против стенда, числа отчёта сверяются с тем, что стенд делал.

| Что задано стендом | Что обязан показать отчёт |
| --- | --- |
| ответ через 200 мс, цель 100 RPS | все перцентили около 200 мс, а не миллисекунды |
| ответ через 400 мс, цель 100 RPS | стенд видит вызовы всю секунду: генератор не ждёт ответа |
| не отвечает никогда, таймаут 200 мс | все вызовы — отказы, цензурированные ровно на таймауте |
| каждый третий вызов — `RESOURCE_EXHAUSTED` | ровно треть отказов; у них время отказа, у остальных — время обслуживания |
| первые 40 вызовов по 50 мс, дальше по 400 мс | p50 в быстрой части, p90 в медленной, не среднее |
| мгновенный ответ, цель 200 RPS | вызовы разложены по секунде ровно, без всплеска в начале |
| **зависание на 1 с посреди прогона**, цель 100 RPS | p99 около секунды, а не миллисекунды — критерий этапа 0а |
| то же при квоте в 2 стрима на стенде | p99 около секунды и p90 не меньше 0,5 с: вызовы, ждавшие стрима внутри генератора, считаются от запланированного момента (coordinated omission) |

Допуск у каждой проверки меньше расстояния до ближайшего правдоподобного неверного ответа:
среднего вместо перцентиля, двойного учёта ожидания, латенси от момента отправки. Запас есть
только сверху; снизу границы строгие, потому что инструмент, страдающий coordinated omission,
врёт вниз.

Числа в отчёте сравниваются не с планом, а с тем, что **стенд записал**: время прихода каждого
вызова — это наблюдение снаружи генератора.

## Чего ещё нет

- упор в потолок in-flight: остановка с вердиктом «цель не держит X RPS» ещё не сделана;
- исключение прогрева: стенд умеет менять задержку по номеру вызова, но не по времени;
- разбивка отказов по категориям в отчёте — пока отчёт считает отказы одной кучей;
- перекрёстная проверка против `ghz` и `k6` на одном стенде;
- точность интенсивности на длинном прогоне: 800 RPS минуту — около 48 000 вызовов без всплесков;
- отказы разных видов (`RESOURCE_EXHAUSTED`, таймаут, `INTERNAL`) как разные категории отчёта.

## Порядок работы

Стенд не зависит от кода движка — только от согласованного контракта. Поэтому работа здесь может
начинаться до того, как движок готов.

Расхождение между ожидаемыми и фактическими числами оформляется через шаблон issue
«Корректность измерений»: он требует описания стенда, расчёта ожидаемого значения и полного
отчёта.
