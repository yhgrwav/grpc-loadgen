# Рабочий процесс: спецификация вперёд кода

Этот документ важнее удобства и важнее скорости. При конфликте с любым другим указанием
действует он.

Принят 2026-09-20.

## 1. README не источник истины

README — документ, который мы **пишем**, а не читаем. Он описывает уже реализованное и отстаёт
от кода.

- **Никогда не выводить требование из README.** Если там написано, что прогрев не попадает в
  отчёт, это означает лишь, что кто-то когда-то так написал, а не что так должно быть.
- **Обнаружив расхождение, не выбирать сторону самостоятельно.** Сформулировать явно: README
  утверждает одно, код делает другое, вот практическая разница для пользователя, вот варианты.
  Решение принимает владелец проекта.
- README дописывается по мере реализации, **в том же PR**. Не заранее, не потом. Только то, что
  уже работает. Обещаний в README нет.

## 2. Порядок работы

Тест, написанный после реализации, фиксирует то, что код делает, а не то, что он должен делать.
Если в реализации ошибка, такой тест закрепляет её как правильное поведение. Это уже случилось:
счётчик отвергнутых наблюдений существовал, никуда не выводился, и все тесты были зелёными —
они проверяли написанное. Дыру нашли обходом чеклиста, а не тестом.

Для каждой задачи:

1. **Спецификация.** Список проверяемых утверждений об ожидаемом поведении. Отдельно — граничные
   случаи и то, чего быть не должно.
2. **Падающие тесты.** По спецификации. Они **обязаны падать**: зелёный тест до реализации не
   проверяет ничего.
3. **Остановиться и показать.** Спецификация и тесты уходят на ревью **до** реализации. Не
   начинать, пока не утверждены. Смысл шага: владелец проекта должен иметь возможность оценить,
   то ли вообще делается, не читая реализацию.
4. **Реализация.** Минимальная, чтобы тесты позеленели.
5. **README.** Дописать то, что теперь работает.

Шаг 3 обязателен.

## 3. Требования к тестам

Набор из одних счастливых путей — неготовая спецификация. Обязаны присутствовать:

- пустой и минимальный вход: ноль наблюдений, один элемент, пустая коллекция;
- границы диапазона: минимальное допустимое, максимальное, на единицу за пределом;
- невозможные значения: отрицательная длительность, нулевой указатель, значение вне перечисления;
- отказ зависимости: что происходит, когда вызываемое возвращает ошибку;
- одновременный доступ, если структура видна из нескольких горутин.

**Нет ни одного теста на границу — спецификация не готова, реализацию начинать нельзя.**

- Тест проверяет одно утверждение, и имя говорит какое: не `TestRecord`, а
  `TestRecord_TimeoutIsStoredAsCensored`.
- Тест не зависит от времени. `time.Sleep` для синхронизации запрещён: на загруженном раннере
  пауза ничего не гарантирует. Проверять инвариант через сигналы и состояние.
- Тест падает, а не висит. Любое ожидание имеет потолок: при регрессии тест обязан упасть, а не
  выесть таймаут CI.
- **Утверждения не стоят под условием.** `if err == nil { проверка }` молча пропускает проверку в
  той ветке, где она нужнее всего. Так уже было: проверка адреса в ошибке `Connect` сидела под
  условием, которое при правильном коде не выполнялось никогда, и половина теста не работала.
  Если тесту нужно ветвиться — это два теста. Если условие зависит от данных таблицы, утверждение
  переписывается так, чтобы проверять обе ветки: `(out.Err == nil) != (code == OK)`.
- **Тест, написанный после реализации, проходит мутационную проверку.** Код ломается намеренно в
  том месте, которое тест должен ловить, и тест обязан покраснеть. Остался зелёным — он ничего не
  проверял. Так найден тест с дедлайном через наносекунду: на Linux он шёл тем же путём, что тест
  с дедлайном в прошлом, а сетевой путь проходил только на Windows, из-за грубых часов.
- **Тест не подгоняется под реализацию.** Не проходит — сначала выясняется, кто неправ. Менять
  тест ради совпадения с кодом без явного решения, что спецификация была неверна, запрещено.

## 4. Где TDD применяется, а где нет

Порядок «спецификация вперёд» универсален. Форма проверки зависит от типа кода.

**Чистая логика с определённым контрактом** — критерий определённости перцентиля, отображение
кодов в категории, правила цензурирования, разбор имени метода. Полный TDD, корнер-кейсы
таблицей.

**Конкурентный код** — воркер-пул, планировщик. Пример-тесты бесполезны: ни один не поймал бы
дедлок. Спецификация формулируется инвариантами, которые обязаны выполняться всегда: «слот
освобождается до записи результата», «после отмены контекста ни одна горутина не остаётся».
Проверка — тест на инвариант, `-race`, прогон под нагрузкой.

**Горячий путь** — запись метрик, отправка. Спецификация включает бюджет по времени и
аллокациям, **бенчмарк пишется до реализации**: «`Record` укладывается в N наносекунд при 500
одновременных горутинах, ноль аллокаций». Такой тест поймал бы сортировку под замком до того,
как она попала в код. Нагрузка в бенчмарке соответствует реальной: при 1000 RPS и ответе в
полсекунды одновременных горутин порядка пятисот, а не восьми. Варьировать надо и `GOMAXPROCS`:
число горутин само по себе ничего не меняет, конкурируют за мьютекс ровно столько потоков,
сколько разрешено планировщику.

**Исследовательская работа** — незнакомый API, reflection. TDD мешает: нельзя писать тест на
неизвестный контракт. Порядок: прототип для выяснения, затем спецификация, тесты, реализация
начисто. Прототип выбрасывается и в PR не попадает.

## 5. Источники истины

Продукт — измерительный прибор. Главный риск не в падении кода, а в том, что он покажет неверное
число и никто не заметит. Тест, написанный тем же, кто писал код, проверяет его же представление
о правильном; неверное представление тест закрепит.

Поэтому требования и проверки берутся **извне проекта**. Мнение любого участника — включая
владельца и любого ИИ-ассистента — само по себе источником истины не является.

По убыванию силы:

**Стенд с заданным поведением.** Сильнейший, потому что истина в нём не утверждается, а задаётся
физически. Заглушка, отвечающая ровно за 200 мс, не мнение о правильном ответе — она создаёт
правильный ответ. Инструмент, сообщивший 5 мс, неправ, и ничья точка зрения в этом выводе не
участвует.

Отсюда различение двух видов тестов:

- *тест-утверждение*: «перцентиль должен считаться вот так». Истина — мнение автора. Полезен, но
  не независим;
- *тест-подстановка*: поведение цели задано конструкцией стенда, инструмент обязан его
  воспроизвести. От мнения автора не зависит.

Для всего, что касается корректности измерений, нужен второй вид. Обязательный набор: известная
постоянная задержка, зависание на известное время, отказы по расписанию, задержка, меняющаяся по
ходу прогона.

**Другой инструмент как перекрёстная проверка.** Один стенд нагружается нами и чужим (`ghz`,
`k6`, для HTTP — `vegeta`); числа обязаны сойтись в пределах заявленной точности. Ценность в том,
что чужой инструмент писали другие люди с другими слепыми зонами. Совпадение двух независимых
реализаций что-то значит; совпадение нашего кода с нашим же тестом — нет. Расхождение не повод
считать неправым чужой инструмент: это повод разобраться, и результат разбора идёт в
`docs/decisions.md` независимо от того, кто оказался прав.

**Трекеры чужих проектов.** Issue в `ghz`, `k6`, `vegeta`, `wrk2` — список требований от людей,
которые реально пользуются такими инструментами. Оттуда берутся: открытые issue как
неудовлетворённые потребности (то, что просят годами, — наша возможная ниша); закрытые «won't
fix» как ограничения, в которые упёрлись другие; **баг-репорты про неверные числа** — самое
ценное, готовый список способов, которыми инструмент такого класса может соврать, каждый
проверяется на нашем коде; обсуждения под изменениями, где видно, какие решения рассматривались.

**Чужая реализация.** Когда неясно, как поступить, смотрится, как сделано у них, и — важнее —
что написано в их обсуждениях и коммитах. Два правила: заимствуется **решение, а не код**
(лицензии разные, копирование создаёт юридическую проблему); чужое решение не считается
правильным по умолчанию — закрытая модель по умолчанию у `ghz` как раз то, чего мы не повторяем.

**Внешняя литература.** Работы по coordinated omission (Гил Тене), статистика цензурированных
наблюдений, документация HdrHistogram. Ссылка кладётся в `docs/decisions.md`, чтобы рассуждение
можно было проверить позже, не восстанавливая заново.

**Специалист по тестированию.** Требования со стороны тестирования приносит человек, для которого
это специальность. Вывести их из общих рассуждений нельзя, попытки — самообман.

**Живой пользователь с настоящим сервисом.** Сильнейший и самый поздний: реальный `.proto`,
реальная нагрузка, реальные ожидания. До его появления остальные источники заменяют его частично.

**Правило.** Решение, влияющее на числа в отчёте, опирается хотя бы на один источник из
перечисленных. «Звучит логично» основанием не является — ни от участника, ни от ассистента. При
записи в `docs/decisions.md` указывается, на чём решение основано: на каком тесте, на чьём issue,
на какой публикации. Решение без источника — гипотеза, и помечается как гипотеза.

## 6. Чего не делать

- Не писать тест после реализации и не называть это TDD.
- Не писать слабый тест, который прошёл бы и на заведомо неверной реализации.
- Не ставить утверждение под условие.
- Не лечить ловушку контракта комментарием «не забудь передать X». Контракт, который зависает или
  врёт без правильного вызова, чинится в контракте.
- Не начинать реализацию до утверждения спецификации.
- Не «приводить код в соответствие с README».
- Не добавлять в README то, что ещё не работает.
- Не принимать решение о том, как считаются числа, на основании «звучит логично».
- Не считать совпадение кода с собственным тестом подтверждением корректности.
- Не отклонять расхождение с чужим инструментом как их ошибку без разбора.
- Не копировать чужой код.
