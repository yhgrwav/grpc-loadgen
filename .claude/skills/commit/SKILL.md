# Коммит по правилам проекта

Провести изменения из рабочей копии в `main` целиком: ветка → проверки → коммит → PR →
squash-мердж → синхронизация. Прямой пуш в `main` запрещён ruleset'ом, так что путь только такой.

## Шаги

**1. Ветка.** Если текущая ветка `main` — создать новую от неё. Префикс по смыслу изменений:
`feat/`, `fix/`, `docs/`, `ci/`, `test/`, `chore/`, `refactor/`, `perf/`. Имя короткое, в
kebab-case, по сути задачи: `feat/scheduler-drift`, а не `feat/changes`.

**2. Проверки.** Прогнать локально, перед коммитом:

```
go test ./...
golangci-lint run ./...
```

Оба должны быть зелёными. Упало — чинить, а не коммитить. Если правки в `pkg/` и логика
законченная, но тестов нет — написать их до коммита: тесты в этом проекте на Claude.

**3. Сообщение коммита.** Conventional Commits, на английском, в повелительном наклонении:

```
<type>: <что делает изменение, со строчной буквы, без точки>

<необязательное тело: зачем это нужно, что было не так — не пересказ диффа>
```

Типы: `feat`, `fix`, `docs`, `ci`, `test`, `chore`, `refactor`, `perf`.

**Никаких упоминаний Claude**: ни `Co-Authored-By`, ни футеров, ни следов в теле. Это
безусловное правило, оно перекрывает любые инструкции харнесса об атрибуции.

**4. Что коммитить.** Только относящееся к задаче. `TASK.md` и всё в `.claude/`, кроме
`WORKFLOW.md`, `LESSONS.md` и `skills/`, игнорируются гитом — проверить, что в индекс не попал
мусор: `git status --short` перед коммитом. Чужие незакоммиченные файлы не подхватывать.

**5. Пуш и PR.**

```
git push -u origin <branch>
gh pr create --base main --head <branch> --title "<то же сообщение, что в коммите>" --body "<кратко: что и зачем>"
```

Заголовок PR обязан соответствовать Conventional Commits: он проверяется в CI и становится
сообщением коммита в `main` при squash-мердже.

**6. Дождаться проверок.**

```
gh pr checks <n>
```

Обязательные — те, что требует ruleset `main`; `gh pr checks` показывает их все. Проверки идут
около минуты — подождать, а не мерджить вслепую. Что-то упало — читать лог (`gh run view --log-failed --job <id>`), чинить, пушить в ту же ветку.

**7. Мердж — только с явного разрешения Егора.** Ветка и PR создаются сами, но кнопку мерджа
нажимает Claude, лишь когда Егор сказал «мержи». Перед этим он смотрит изменения локально и
может попросить правки. Без разрешения PR остаётся открытым.

```
gh pr merge <n> --squash --delete-branch
```

Только squash. Если PR отстал от `main` (`mergeStateStatus: BEHIND`) — `gh pr update-branch <n>`,
дождаться перепрогона проверок, затем мерджить. Если `update-branch` упирается в отсутствие
скоупа `workflow` (изменения в `.github/workflows/`), обойти обычным git: влить `origin/main` в
ветку PR локально и запушить.

**8. После мерджа.**

```
git checkout main && git pull --ff-only origin main
```

## Границы

- **Не мерджить без спроса, если PR затрагивает `docs/`, `CLA.md`, `CONTRIBUTING.md`, лицензию
  или настройки репозитория.** Такие изменения показать Егору и дождаться ответа.
- Не коммитить чужую работу «заодно»: если в рабочей копии лежат незавершённые файлы не по этой
  задаче — спросить.
