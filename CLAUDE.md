# grpc-loadgen

CLI для нагрузочного тестирования gRPC-сервисов на Go. Pet-проект Егора с прицелом на
коммерциализацию: ядро и CLI открытые (Apache 2.0), платный control plane — позже, в отдельном
закрытом репозитории.

Назначение: по результату прогона пользователь пишет разработчикам отчёт — **при какой нагрузке
система перестаёт справляться и где узкое место**. Разный RPS на методы, сценарии, разложение
латенси — средства, а не цель. Генератор видит только клиентскую сторону: ресурсы цели не
выводить из клиентских данных. Назначение, этапы и что решено не делать — `docs/strategy.md`,
читать при планировании этапа и при споре о приоритете.

## Как работаем

- **Спецификация вперёд кода.** Сначала список проверяемых утверждений и падающие тесты по ним,
  потом остановка и показ Егору, и только после утверждения — реализация. Шаг с показом
  обязателен. Полностью — в `.claude/WORKFLOW.md`, он важнее удобства и скорости.
- **README не источник требований.** Он описывает уже сделанное и отстаёт от кода. Расхождение
  README с кодом — открытый вопрос к Егору, а не задача «привести код в соответствие».
- **Числа в отчёте требуют внешнего источника.** Стенд с заданным поведением, чужой инструмент,
  issue в чужих трекерах, публикация. «Звучит логично» основанием не является — ни от Егора, ни
  от Claude. Решение без источника помечается в `docs/decisions.md` как гипотеза.
- **Код пишет Claude.** Егор ставит цель — Claude проектирует, реализует, тестирует и отвечает
  за результат.
- **Подагентов не использовать.** Ни для кода, ни для ревью, ни для поиска. Подагент стартует
  холодным и тратит десятки тысяч токенов на пересказ того, что уже есть в этом контексте.
  Всё делается здесь, своими руками.
- **Спорное решаем по пользователю.** Нет очевидного ответа — выигрывает вариант, который не
  создаёт пользователю сюрприза: неявного правила, которое надо выучить, числа, которое может
  молча соврать, поля, действие которого не угадывается. Приоритеты: корректность измерений >
  удобство > скорость.
- **Спрашивать — только по продуктовым развилкам.** Что за инструмент мы делаем и для кого —
  к Егору. Как это устроено внутри — решает Claude.
- **Коротко.** Маленький вопрос — маленький ответ.
- **Ревизия перед каждым PR** — скилл `/review`: классы цены ошибки, порядок обхода, константы
  проекта. Находка без сценария с числами не засчитывается.
- **Объяснения по запросу** (`/explain`), а не вплетённые в каждый шаг.

## Правила кода

- Комментарий пишем только там, где он сообщает то, чего не говорит имя: формат аргумента,
  неочевидное поведение, предупреждение. Пересказ сигнатуры — нет. Линтер это не требует,
  решает автор. Doc-комментарий пакета в `doc.go` обязателен (`revive`, pkg.go.dev).
- «Почему» живёт в `docs/decisions.md`.
- Коммиты и PR — **без единого упоминания Claude**: ни `Co-Authored-By`, ни футеров.
- Сообщения коммитов на английском, документация для нас — на русском.

## Архитектура

Три слоя, разделены с первого коммита:

1. `pkg/*` — библиотека. Не знает ни про YAML, ни про CLI, ни про control plane.
2. `cmd/grpc-loadgen` — тонкая обёртка: конфиг → ядро → отчёт → exit code.
3. Control plane — потом, другой репозиторий.

```
cmd/grpc-loadgen/   точка входа CLI
pkg/engine/         планировщик, rate limiting, потолок in-flight, воркер-пул
pkg/descriptor/     дескрипторы методов через gRPC server reflection
pkg/metrics/        HDR-гистограммы, цензурированные наблюдения, percentiles
pkg/config/         парсинг и валидация конфига
internal/clock/     абстракция времени для тестов
```

**Логирования в `pkg/` нет.** Библиотека возвращает ошибки и события, печатает их CLI.
Отчёт → stdout, прогресс и ошибки → stderr.

Зафиксированные решения — в `docs/decisions.md`: open model, латенси от `scheduledAt`, абсолютный
дедлайн, три слагаемых латенси, разделение каналов отказа отправителя, упор в in-flight cap —
остановка с вердиктом, percentiles не усредняются, данные во времени (итог отдельно от окон),
единица расписания — итерация, reflection, только unary в MVP.

Переоткрывать их можно, но только с новой причиной и с переписыванием раздела: решение, которому
код перестал соответствовать, хуже отсутствия решения.

**Ядро и фичи.** Ядро — планировщик, воркер-пул, отправитель, метрики; всё остальное опции поверх
него. Фича не имеет права усложнять горячий путь: выключена — её нет в цикле отправки вообще.
Ядро не знает про фичи, фичи не знают друг про друга, формат конфига расширяется, а не
переписывается. Подробнее в `docs/strategy.md`.

## Окружение

- Go 1.26.1 в `C:\Users\yeahgor\go\go1.26.1\bin`, прописан в PATH. `golangci-lint` v2 в `~/go/bin`.
- Планка в `go.mod` следует за зависимостями: требует свежая библиотека версию выше — поднимаем

  сборку, иначе закрытый control plane невозможен), сборка.
- Зависимости: только Apache-2.0 / MIT / BSD / ISC. Парсер YAML — `goccy/go-yaml`.

## Файлы процесса

В гите — чтобы свежий клон, worktree и ревьюер видели правила проекта:

- `CLAUDE.md` — этот файл.
- `.claude/WORKFLOW.md` — порядок работы, требования к тестам, источники истины. Важнее всего
  остального при конфликте.
- `.claude/LESSONS.md` — грабли проекта, по строке на урок. Читать перед работой.
- `.claude/skills/` — `/review` (ревизия), `/commit`, `/session-start`, `/session-end`.
- `docs/strategy.md` — назначение, этапы, что решено не делать.

Локально, в гите нет:

- `TASK.md` — единственный файл состояния: в работе, следующее, вопросы, техдолг, идеи.
  Перезаписывается целиком в конце работы, а не дописывается.
- `.claude/STRATEGY.md` — название продукта до решения.
