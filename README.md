---

> **Ранняя стадия.** Работает: unary-нагрузка на настоящий сервис, несколько методов со своим
> RPS в одном прогоне, тело запроса из конфига, отчёт в консоль. Ещё нет: разгона, порогов
> pass/fail для CI, JSON-отчёта, экспорта метрик. Ниже описано только то, что уже работает.

Инструмент отвечает на вопрос, с которым приходят к нагрузочному тесту: **при какой нагрузке
сервис перестаёт справляться и где узкое место.** Для этого он даёт нагрузку, похожую на
настоящую, — несколько методов одновременно, у каждого свой RPS, — и меряет так, чтобы числа не
врали, когда сервис деградирует. Ни `.proto`, ни кодогенерации, ни скриптов.

Проект держится на трёх приоритетах, в этом порядке.

**Корректность измерений** — числа соответствуют тому, что происходило на самом деле, в том
числе когда сервис деградирует.

**Удобство.** В этой категории принято считать, что инструмент для инженеров может быть
неудобным. Я считаю иначе: интерфейс — одно из главных преимуществ продукта, а неясное
сообщение об ошибке такой же дефект, как неверное число.

**Скорость** — генератор не становится узким местом.

## Установка

```console
$ go install github.com/yhgrwav/leettest/cmd/leettest@latest
```

## Конфиг

```yaml
app:
  target:
    ip: localhost
    port: 50051
  tls: false

load:
  warmup: 5s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m

    - method: wallet.v1.WalletService/Transfer
      rps: 50
      duration: 1m
```

Имя метода — полное: `пакет.Сервис/Метод`. Описание метода инструмент получает у самого
сервиса через gRPC server reflection, поэтому класть куда-то `.proto` не нужно.

| Поле | Что делает |
|---|---|
| `name` | Необязательно. Как назвать прогон в заголовке. Не указано — имя сервиса, если все методы из одного, иначе имя файла конфига |
| `app.target` | Адрес сервиса: `ip` и `port` |
| `app.tls` | TLS. Не указан — включён. `false` — подключение без шифрования |
| `app.ca` | PEM-файл с сертификатами, которым проверять сервис вместо системных. Нужен TLS |
| `app.cert`, `app.key` | Клиентский сертификат и его ключ в PEM, для сервиса с mTLS. Только вместе, нужен TLS |
| `app.server_name` | Имя, по которому проверять сертификат сервиса, если он не называет адрес из `target`. Нужен TLS |
| `app.metadata` | Заголовки каждого вызова: `authorization`, `x-api-key` и т. п. `${ИМЯ}` берётся из переменной окружения |
| `app.max_response_size` | Самый большой ответ, который примет вызов: `16MiB`, `512KB`. Единица обязательна (`MB` = 10⁶ байт, `MiB` = 2²⁰), меньше 2 GiB. Не указан — 4 MiB, как у gRPC. Ответ больше — отказ запроса, а не перегрузка цели |
| `load.warmup` | Первые N секунд не попадают в percentiles и в `sent`: холодные кеши их портят. Вызовы прогрева уходят к цели, отчёт печатает их строкой `warm-up N sent (M failed), excluded from stats` — `sent` плюс она равны всем ушедшим вызовам. Цель получила их все, кроме посчитанных как unreachable; `cut off` и вызовы с тайм-аутом могли дойти до неё не полностью: цель, которая не открывает окно HTTP/2 (flow control), получает только заголовки, и её счётчики вызов не увидят. Входит в `duration`, короче любого вызова |
| `load.calls[].method` | Полное имя метода |
| `load.calls[].rps` | Запросов в секунду для этого метода |
| `load.calls[].duration` | Сколько его нагружать: `30s`, `5m`, `1h` |
| `load.calls[].timeout` | Сколько ждать ответа. Не указан — `2s`. Ноль не отключает, а даёт ошибку |
| `load.calls[].data` | Тело запроса, см. ниже. Не указано — пустое сообщение |

Конфиг читается строго: опечатка в имени поля — ошибка с номером строки, неверное значение —
ошибка с номером вызова и его методом, а не прогон с пустой нагрузкой. `rps` — целое число:
`10.5` отклоняется, а не округляется молча до десяти. `warmup` обязан быть короче каждого вызова,
иначе от вызова не осталось бы ни одного измеренного запроса.

**Таймаут и потолок запросов в полёте.** Если сервис завис, каждый метод держит в полёте
`rps × timeout` запросов, пока не сработает таймаут, плюс запас: один запрос на границе окна и
`rps × 100 мс` на то, что генератор освобождает место чуть позже дедлайна. Сумма по методам не
должна превышать `-max-in-flight` (по умолчанию 5000). Это проверяется до старта, ошибка называет
оба выхода: какой таймаут влезет и какой нужен потолок. Поэтому зависший сервис в потолок не
упирается: прогон доходит до конца, а отчёт говорит, сколько вызовов не получили ответа за
таймаут и на каком вызове по плану цель ответила в последний раз. Если потолок всё же кончился, место держали дольше
дедлайна больше чем на 100 мс — это генератор (не хватило процессора) или отправитель, и отчёт
объявляет прогон недействительным. Рядом печатается, сколько слотов в момент упора держались
после своего дедлайна. Сколько из них вышли за запас, инструмент не считает: для вердикта хватает
одного.

### Доступ к сервису

```yaml
app:
  target:
    ip: 10.0.3.17
    port: 443
  ca: certs/ca.pem            # пути — относительно файла конфига
  cert: certs/client.pem
  key: certs/client.key
  server_name: payments.internal
  metadata:
    authorization: Bearer ${PAYMENTS_TOKEN}
    x-api-key: ${PAYMENTS_KEY}
```

**Секреты.** `${ИМЯ}` подставляется из переменной окружения, в том числе внутри значения:
`Bearer ${TOKEN}`. Переменная не задана или задана пустой — ошибка до старта с её именем. Иначе
ушёл бы `Bearer ` без токена, и прогон показал бы 100% отказов как вину цели. Чтобы написать
`${` буквально, удвойте доллар: `$${`. Одиночный `$` остаётся как есть. Подстановка работает
только в `app.metadata`: в `data`, `target` и остальных полях `${ИМЯ}` уходит как написано.
Флага для заголовков нет, поэтому токен не попадает ни в `ps`, ни в историю shell. Значения
заголовков инструмент не печатает нигде: ни в отчёте, ни в ходе прогона, ни в ошибках.

**Заголовки.** Имена приводятся к нижнему регистру, как их и передаёт HTTP/2. Ошибка конфига до
старта: ключ с `grpc-` (его резервирует gRPC), псевдозаголовки вроде `:path`, ключ с `-bin`
(бинарные заголовки пока не поддерживаются), значение вне печатаемого ASCII. Те же заголовки и
сертификат уходят в проверку методов перед стартом. Если цель на ней ответила `Unauthenticated`,
а заголовки заданы, прогон не начнётся: «target rejected credentials», — с неверным токеном он
показал бы ошибку конфига как результат цели. `PermissionDenied` прогон не останавливает: токен
принят и может работать для вызовов, не пуская к reflection; методы помечаются непроверенными.
`Unauthenticated` без заголовков тоже не останавливает, а в заметке сказано: «target requires
credentials; app.metadata is not set».

**Сертификаты.** `ca` заменяет системные корни, а не добавляется к ним. Проверка сертификата
цели не отключается ничем. `server_name` меняет только имя, с которым сверяется сертификат и
которое уходит в SNI; `:authority` остаётся адресом из `target`, так что цель, которая
маршрутизирует по нему, видит тот же запрос. Зашифрованный паролем ключ не поддерживается: его
нужно расшифровать заранее.

**Одно соединение, service config цели игнорируется.** Генератор держит одно соединение к
одному адресу. Если DNS отдаёт несколько адресов, нагружается только один бэкенд: балансировки
между ними нет. Отчёт этого не показывает: сколько адресов отдал DNS, он не знает. Service config, который цель
отдаёт через резолвер, не применяется: он мог бы открыть соединение к каждому адресу, укоротить
наш таймаут, держать вызовы на упавшем соединении вместо отказа или ограничить размер ответа —
то есть изменить то, что измеряется. Повторов вызовов тоже нет.

**Ошибки до старта.** Всё, что можно узнать до прогона, — код выхода 1 и ни одного вызова к
цели: файл не найден или не PEM, сертификат не подходит к ключу, сертификат цели просрочен или
не называет адрес (подсказка — `server_name`), цель закрыла соединение сразу после
рукопожатия (не приняла клиентский сертификат), TLS включён, а цель без него, или наоборот.

### Тело запроса

```yaml
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      data:
        wallet_id: "w-123"
        currency: USD                         # enum — по имени
        filter:
          since: "2026-01-01T00:00:00Z"       # google.protobuf.Timestamp
```

`data` — обычный YAML в форме сообщения. Схему инструмент берёт у сервиса через server
reflection; `.proto` не нужен. Тело собирается один раз до старта, и любая ошибка в нём —
неизвестное поле, не тот тип, несуществующий метод — видна сразу, с именем метода и поля, до
первого запроса. Нет `data` — уходит пустое сообщение, и reflection такому методу не нужен.

**Одно тело на метод.** Все вызовы метода уходят с одним и тем же `data`. Для записи с ключом
идемпотентности это значит, что первый вызов создаёт запись, а все следующие идут по пути повтора:
цель отдаёт уже сохранённый ответ. Меряется этот путь, а не создание записи. Разные данные на
каждый вызов — в планах.

Правила значений — стандартные правила JSON для protobuf (`protojson`):

- имя поля — как в `.proto` (`wallet_id`) или в JSON-форме (`walletId`);
- enum — по имени; `Timestamp`, `Duration` — строкой в их формате;
- `int64` и `uint64` доходят точно, в том числе больше 2^53 (snowflake-ID, суммы в минимальных
  единицах): число нигде не проходит через float;
- число с ведущим нулём (`0123`, `007`) — ошибка конфига: YAML прочитал бы его как восьмеричное.
  Нужен ноль — пишите строкой, `"0123"`;
- **`bytes` — строкой в base64.** `signature: abcd` — это не четыре байта `abcd`, а три других
  байта: `abcd` сам по себе валидный base64, и ошибки не будет. Четыре байта `abcd` пишутся как
  `signature: YWJjZA==`.

Каждый метод из конфига проверяется у сервиса до старта: опечатка в имени или метод, которого там
нет, — ошибка до первого запроса, а не прогон, где все вызовы падают с `Unimplemented`.

Если reflection на сервисе выключен, метод с `data` не запустится — ошибка скажет это прямо.
Метод без `data` работает и без reflection: проверить его нечем, и об этом печатается
предупреждение — перед прогоном в stderr и ещё раз строкой в отчёте, потому что полноэкранный вид
первое затирает. В предупреждении сказано, почему проверить не удалось: reflection выключен, либо
он ответил отказом или не ответил вовсе — это разные вещи.

## Запуск

```console
$ leettest -c leettest.yaml
```

До старта инструмент подключается к сервису. Недоступный адрес — ошибка сразу, с адресом и
причиной, без прогона и без отчёта.

**Где запускать.** Ставьте генератор рядом с целью: в той же сети, на той же машине или в том же
кластере. Всё, что лежит между ними, входит в латенси и выглядит как время цели. На нашем стенде
при 1000 RPS генератор на хосте через проброс портов Docker Desktop показал p99 38 мс, а внутри
сети Docker — 2 мс: цель одна и та же, в первом случае мерили сеть Docker, а не её.

| Флаг | Что делает |
|---|---|
| `-c` | Путь к конфигу |
| `-connect-timeout` | Сколько ждать сервис, который принял соединение, но молчит. По умолчанию `10s`. Отказ в соединении и неверный адрес не ждут |
| `-max-in-flight` | Потолок запросов, ждущих ответа. По умолчанию `5000` |
| `-fake` | Нагружать встроенную заглушку вместо сервиса из конфига — посмотреть на инструмент без сервиса. Отчёт помечен `fake target` |
| `-fake-delay`, `-fake-jitter`, `-fake-fail-ratio` | Поведение заглушки. Только вместе с `-fake` |
| `-version` | Напечатать версию и выйти. Собранное из исходников печатает коммит |

В терминале прогон идёт в полноэкранном виде: RPS, запросы в полёте, ошибки и percentiles в
реальном времени, `q` — остановить. Без терминала (в CI, при перенаправлении вывода) — строка
прогресса раз в секунду:

```
32.0s  sent 25600  rps 800  in-flight 47  failed 51  not-sent 0  p99 43ms
```

В конце — отчёт по каждому методу: отправлено, отказов, `sent/s`, p50/p90/p95/p99. `sent/s` — это
отправленные запросы, делённые на время отправки: прогрев и ожидание последних ответов после конца
плана в него не входят, поэтому подвисание цели в конце прогона не занижает эту цифру. Запросы, оборванные
таймаутом, не подменяются числом: если они могли бы занять место перцентиля, он печатается
нижней границей, `>2.0s`. Запросы, не дошедшие до сервиса, считаются отказами, но в percentiles не
попадают. Запрос, который ушёл, но статуса не получил — другая сторона сбросила стрим или оборвала
соединение, — считается отдельно, как `cut off`: цель или прокси могли его обработать, для записи это
повод проверить дубли.

Отказы разделены: строка `error status` — сколько раз вернулся статус ошибки (`RESOURCE_EXHAUSTED`,
`UNAVAILABLE`, `INTERNAL` и другие) и через сколько. Статус мог прислать не сама цель, а прокси перед
ней: nginx без живого бэкенда отвечает `UNAVAILABLE`, и клиент одно от другого не отличит. Строка `rejected` — сколько раз вызов провалился бы при любом
темпе: неверный запрос (нет такого метода, неверный аргумент, тело не по схеме) или сообщение,
которое не поместилось — ответ, целиком отклонённый лимитом клиента в 4 МБ (ничего из него не
доходит), либо запрос, который цель или прокси перед ней сочли слишком большим (их лимит нам неизвестен). Второе от нагрузки не
зависит: такой вызов провалится при любом RPS. Если все измеренные вызовы метода отвергнуты,
прогон объявляется недействительным, и вердикт называет этот метод: по одной опечатке из трёх
методов доля по прогону была бы 33%, и никакого вердикта.

Под отчётом упавшие вызовы каждого метода разложены по кодам gRPC, от частого к редкому, в двух
строках. «sent by the target» — статус пришёл по сети: от цели или от прокси перед ней, отличить
их клиент не может. «set by the client, no status came back» — статуса не было, код поставил сам
клиент: никто не ответил, стрим сброшен другой стороной, истёк наш дедлайн. Один и тот же код
бывает в обеих строках. `DeadlineExceeded` от цели обычно наш же дедлайн: он уходит цели в
заголовке `grpc-timeout`, и она может прервать вызов раньше нашего таймера. Категория говорит,
чья это вина, код — что искать в логах цели.

Нагрузка идёт по одному соединению. Отчёт печатает, сколько раз оно переподключалось и какой
лимит одновременных стримов (`MAX_CONCURRENT_STREAMS`) объявила цель, или что она его не объявила.
Вызов считается от запланированного момента, и всё, что он прождал на стороне клиента, входит в
его латенси: опоздание генератора, ожидание готового соединения, ожидание свободного стрима. Если
без этих ожиданий меняется напечатанный p99 хотя бы одного метода или часть вызовов так и не ушла,
отчёт выносит вердикт и называет причину, которая больше других встречается в хвосте p99: опоздал
генератор, не было соединения с целью, кончились стримы. В последнем случае ёмкость цели выше
«лимит × соединения» вызовов в полёте не измерена. Для каждого затронутого метода печатается p99
без ожиданий на стороне клиента — время, которое вызов провёл у цели. Если перед вызовом ждали
резолвер, в ожидание соединения попадают и интерсепторы вызывающего, поэтому это число может выйти
немного заниженным. Неотправленные вызовы разбиты по причинам: ждали стрим, ждали соединение,
опоздал генератор.

Отчёт идёт в stdout, прогресс и ошибки — в stderr.

**Остановка** (`q` в полноэкранном виде, Ctrl+C без него):

- первое нажатие — новые запросы не уходят, запросы в полёте дорабатывают до своего таймаута и
  попадают в отчёт как обычно;
- второе — запросы в полёте обрываются и считаются отдельно как оборванные: не отказ сервиса, а
  нижняя граница времени; отчёт печатается;
- третье — выход сразу, без отчёта.

В полноэкранном виде верхняя строка ведёт по этим ступеням: пока запросы в полёте дорабатывают, она
показывает, сколько их осталось и что `q` ещё раз их оборвёт; после обрыва — что `q` ещё раз выйдет
без отчёта.

SIGTERM (`docker stop`, Kubernetes, отмена джоба в CI) сразу обрывает запросы в полёте и
печатает отчёт, минуя мягкую остановку: оркестратор через несколько секунд убивает процесс, и
отчёт должен успеть выйти. Если обрыв уже идёт, SIGTERM его не прерывает.

Остановленный прогон помечается в отчёте как неполный: числа в нём честные, но покрывают меньше,
чем было запланировано.

**Коды возврата.** Порогов «держит / не держит» пока нет, поэтому дошедший до конца прогон
возвращает `0`, как бы цель ни отвечала: **`0` не значит «сервис здоров»**. Прогон, где 100%
вызовов не получили ответа, тоже вернёт `0` — отчёт при этом прямо об этом говорит. Порог и
ненулевой код по нему появятся на этапе 2. Коды ранжированы, а не складываются: недействительный
прогон (`2`) важнее неполного (`3`), а `130` и `143` — это выход без отчёта, поэтому остановка,
которая отчёт напечатала, всегда `3`.

| Код | Что случилось |
|---|---|
| `0` | План выполнен, отчёт полный |
| `1` | Прогон не состоялся: флаги, конфиг, подключение. Отчёта нет |
| `2` | Прогон недействителен: упёрся в потолок in-flight, или цель отвергла все вызовы какого-то метода как неверный запрос. Отчёт есть, но числа не про цель |
| `3` | Прогон остановлен раньше плана. Отчёт есть и покрывает только то, что успело пройти |
| `130` | Аварийный выход без отчёта после Ctrl+C |
| `143` | Аварийный выход без отчёта после SIGTERM |

Разгона с нуля до целевого RPS, порогов pass/fail и JSON-отчёта для CI, экспорта в
