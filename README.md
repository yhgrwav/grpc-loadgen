# grpc-loadgen

**Русский** · [English](README.en.md) · [Deutsch](README.de.md) · [中文](README.zh-CN.md)

Декларативное нагрузочное тестирование gRPC-сервисов.

> **Статус: ранний WIP.** Репозиторий — скелет, движок ещё не реализован.
> Ничего из описанного ниже пока не работает; вид CLI и конфига приведён, чтобы зафиксировать UX.

## Задача

Существующие инструменты каждый по-своему не закрывают реальный сценарий нагрузки:

| | разный RPS на несколько методов в одном прогоне | зависимости между вызовами | латенси без coordinated omission | без кодогенерации и `.proto` |
|---|---|---|---|---|
| `ghz` | нет — один метод на запуск | нет | частично | да (reflection) |
| `k6` (grpc) | скриптом, по умолчанию closed model | вручную | closed model скрывает простои | нужен `.proto` |
| jmeter-grpc-request | неудобно | вручную | нет | нужен `.proto` |
| **grpc-loadgen** | да | планируется (этап 1) | да, by design | да (reflection) |

Конкретно: нужно одновременно долбить `GetBalance` на 800 RPS, `Transfer` на 50 RPS и
`CreateWallet` на 5 RPS — один сервис, один прогон, один отчёт.

## Технические решения

**Open model.** Целевой RPS — это расписание, а не уровень параллелизма: запросы уходят по
часам независимо от того, вернулись ли предыдущие. Closed model (N виртуальных юзеров, каждый
ждёт ответа) сама себя троттлит ровно в тот момент, когда сервис начинает деградировать, —
то есть именно тогда, когда его и надо измерить.

**Латенси считается от `scheduledAt`.** При цели 1000 RPS (запрос каждую 1 мс) сервис зависает
на секунду. За это время должно было уйти 1000 запросов.
Если мерить от момента фактической отправки — все они уходят после того, как сервис отвис,
каждый отрабатывает за 5 мс, и отчёт показывает `p99 = 5ms`: секундный простой исчез.
Если мерить от момента, на который запрос был *запланирован*, — запрос на `t=0` реально ушёл в
`t=1000ms`, ответ пришёл в `t=1005ms`: латенси `1005ms`. Один и тот же прогон, два отчёта,
правдив только один. Это заложено в ядро с первого коммита, а не прикручено сбоку.

**Явный потолок in-flight.** При open model зависшая цель копит висящие запросы, пока генератор
не умрёт раньше тестируемого сервиса. Упор в потолок считается ошибкой прогона — и никогда
молчаливым снижением подаваемой нагрузки, которое незаметно обесценило бы результаты.

**Метрики, которые складываются.** Запись идёт на hot path: HDR-гистограммы и sharded counters,
а не мьютекс вокруг слайса. Percentiles считаются по слитым гистограммам и никогда не
усредняются — среднее из p99 не значит ничего, а распределённый запуск (этап 3) обязан сливать
именно распределения.

**Дескрипторы через gRPC server reflection.** Ни кодогенерации, ни `.proto` класть никуда не
нужно. Работа идёт на уровне protobuf wire format, поэтому язык тестируемого сервиса роли не
играет. Парсинг `.proto` (в процессе, без внешнего `protoc`) — фолбэк этапа 2 для сервисов с
выключенным reflection.

**В MVP только unary RPC.** Streaming — в roadmap.

## Как это будет выглядеть

```yaml
# loadgen.yaml
target:
  address: localhost:50051
  plaintext: true

defaults:
  duration: 60s
  max_in_flight: 5000

calls:
  - method: wallet.v1.WalletService/GetBalance
    rps: 800
    payload:
      wallet_id: "w-0001"

  - method: wallet.v1.WalletService/Transfer
    rps: 50
    payload:
      from: "w-0001"
      to: "w-0002"
      amount: 100

thresholds:          # опционально; превышение -> exit code 1
  - metric: p99
    less_than: 200ms
  - metric: error_rate
    less_than: 0.01
```

```console
$ grpc-loadgen run -c loadgen.yaml
```

Пороги — это то, что делает инструмент пригодным для CI: в норме отчёт и exit 0, при превышении
отчёт и exit 1, чтобы пайплайн упал.

## Roadmap

- **Этап 0 (MVP)** — движок нагрузки без зависимостей между вызовами: reflection, конфиг со списком `{method, rps, duration}`, статический payload на метод, отчёт с percentiles, опциональные пороги.
- **Этап 1** — граф зависимостей между вызовами: пул живых сущностей (создали кошельки — переиспользуем их id в транзакциях), producer-consumer между потоками запросов, явное поведение при истощении пула (backpressure).
- **Этап 2** — `.proto` как источник дескрипторов, streaming RPC, кастомные protobuf-опции для авто-связывания, контейнеризация.
- **Этап 3** — control plane: распределённый запуск, агрегация гистограмм с нескольких машин, синхронизация старта воркеров, дашборд. Отдельный закрытый репозиторий.

## Структура

```
cmd/grpc-loadgen/   точка входа CLI
pkg/engine/         планировщик, rate limiting, потолок in-flight, воркер-пул
pkg/descriptor/     получение дескрипторов методов (reflection)
pkg/metrics/        гистограммы, sharded counters, percentiles
pkg/config/         парсинг и валидация конфига
internal/           приватные хелперы
```

Ядро-библиотека ничего не знает ни про YAML, ни про CLI, ни про будущий control plane. Способы
доставки зависят от ядра; ядро не зависит ни от одного из них.
